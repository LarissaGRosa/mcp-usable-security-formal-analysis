Secure email — annotated interface mockups

Proposed sender and recipient interfaces for a generic secure-webmail, covering all three sending methods. Every numbered marker is an element a user can interact with; the legend follows each mockup.

These are design mockups, not screenshots of a shipping product. They illustrate how the flows and out-of-band steps could be surfaced in a UI.

  1. Window controls — minimize, expand to full screen, close/discard.
  2. To field — type or paste addresses; each becomes a removable chip.
  3. Per-recipient encryption indicator — the lock on each chip shows that recipient's state: closed lock (alice) = a key is on file, so end-to-end is possible; open amber lock (bob) = no key. This is the cue to choose a password.
  4. Cc/Bcc toggle — reveals the carbon-copy fields.
  5. Subject field — with the standing reminder that the subject is never encrypted.
  6. Encryption-mode selector — the main control; opens the method menu.
  7. Encryption menu — the three methods, each showing whether it's usable for the current recipients; the selected one is checked.
  8. Message password — the passphrase protecting the message in password mode.
  9. Show/hide password — reveals the typed password to check it.
  10. Hint field — travels inside the email, so keep it vague.
  11. Expiration — sets a self-destruct timer.
  12. Attach — add files, encrypted with the body.
  13. Sign · attach my key — digitally sign, and/or include your public key so replies can be encrypted back.
  14. Body editor and toolbar — the message content.
  15. Send — dispatches using the chosen encryption.
  16. Discard — deletes the draft.

  1. Password field — the passphrase shared out-of-band.
  2. Show/hide password — reveals it to check for typos.
  3. Show hint — reveals the vague hint set in the composer.
  4. Unlock — decrypts and opens the message.

  6. Reply box — compose a response.
  7. Send reply — encrypted straight back to the sender, staying on the secure channel.
  8. Expiration notice — time before the message self-destructs (informational).
  9. Language selector — switches the page language for any recipient.

3. Recipient — end-to-end message in the inbox

A recipient who has keys never sees a gate — the message arrives decrypted. The interactions are about verifying trust and replying.

  1. Encryption badge — tap for encryption details (cipher, that it was end-to-end).
  2. Signature-verified badge — tap to see which key signed it and whether it's confirmed as the sender's.
  3. Trusted-key indicator — the sender's key is on file and verified; tapping opens the key/fingerprint to check or re-verify.
  4. Message body — decrypted automatically with the reader's private key.
  5. Encrypted attachment — downloads and decrypts locally; the lock glyph marks it encrypted at rest.
  6. Reply — automatically encrypted back to the sender.
  7. Forward — re-encrypts to the new recipient's key if one exists.
  8. More actions — overflow menu (view original/headers, block sender, report).

Design notes

  • The most important control is the per-recipient lock indicator (sender marker 3): it drives the whole decision, signalling when to switch from end-to-end to a password.
  • The recipient experience splits by method: password recipients get a self-contained web page where the password is the only gate; key-holding recipients never see a gate and instead get trust signals (badges) to confirm authenticity.
  • The out-of-band steps stay out of these screens by design: the password never appears in the UI you send, and key verification happens through the key/fingerprint view (inbox marker 3), not inline.
