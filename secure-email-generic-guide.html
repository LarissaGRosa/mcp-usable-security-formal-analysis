Sending secure email — a generic guide

A provider-agnostic view of how to send secure email, drawn from three privacy-focused providers — Proton Mail, Mailfence, and mailbox.org. Their interfaces differ, but the ways to actually send a secure message reduce to the same three methods, all built on the open standards TLS and OpenPGP.

Each provider labels features differently and changes its interface over time. This guide describes the shared concepts and flows; for exact button names and current options, check each provider's help center (linked at the end).

The three providers in brief

  • Proton Mail — automates key management most aggressively: messages between two Proton users are end-to-end encrypted with no setup, because Proton publishes and fetches public keys through its own key server. External encryption uses standard OpenPGP (imported keys or Web Key Directory).
  • Mailfence — standards-explicit OpenPGP built into the webmail, with an integrated keystore for generating, importing, publishing, and managing keys, plus a symmetric "encrypt with a password" option.
  • mailbox.org — provides Guard, an in-browser OpenPGP system, and also supports S/MIME and an encrypted mailbox (incoming mail re-encrypted to your key for storage at rest), plus a password-protected option for keyless recipients.

The core idea

Every secure-email method comes down to getting a key or a secret to the other person over a channel you can trust. The three methods differ only in how that happens — and that single difference explains everything about their setup cost and strength.

What encryption protects (and what it does not)

  • Protected: the message body and attachments, when end-to-end or password encryption is in effect.
  • Not protected: the subject line and envelope metadata (sender, recipient, timestamps). These route the mail and are not encrypted end-to-end in any of the three. Keep sensitive details out of the subject line.

Method 1 — Transport encryption (TLS)

How it works

The baseline that every modern email gets automatically: the connection between mail servers is encrypted with TLS, so the message is protected while in transit. It is not end-to-end — each provider can read the message on its servers (unless a mailbox-at-rest encryption option is enabled). All three providers do this for ordinary mail with no action from you.

Before you start

  • Nothing. Both the sending and receiving providers support TLS — which virtually all do today.

Secondary / out-of-band channel

  • None. The providers negotiate the encrypted connection automatically.

Trust model and caveats

  • Protects against eavesdroppers on the network, not against the providers themselves.
  • If either server does not enforce TLS, the message may travel unencrypted. Use Method 2 or 3 when the content is sensitive.

Method 2 — End-to-end with OpenPGP

How it works

The strongest, standards-based method, supported by all three providers (and interoperable with any OpenPGP user anywhere). You encrypt to the recipient's public key and sign with your private key; only their private key can decrypt. The provider never sees the plaintext. Proton does this automatically between Proton users; Mailfence and mailbox.org expose explicit key management in the webmail.

Before you start

  • You have your own key pair (generated or stored in the provider's webmail/keystore).
  • The recipient has their own key pair and a client that can decrypt with their private key.

Secondary / out-of-band channel

  • The recipient's public key — obtained from them directly, from a public keyserver, or auto-discovered via Web Key Directory (WKD).
  • Fingerprint verification — confirm the key really belongs to that person through a separate channel. Holding a key does not by itself prove identity.
  • Reciprocal: for the recipient to verify your signature or reply encrypted, they need your public key.

Trust model and caveats

  • Strongest method; the provider cannot read the message. Interoperable across providers and standalone PGP tools.
  • Security rests on the correct key plus a verified fingerprint. Skipping verification is the usual weak point.
  • Most setup of the three; both sides need keys and compatible software.

Method 3 — Password-based encryption

How it works

The fallback for reaching someone who has no keys. You protect the message with a passphrase; it is encrypted symmetrically and delivered either as an encrypted message or as a secure link. The recipient enters the password — obtained separately — to read it, and can usually reply securely. All three providers offer a version of this.

Before you start

  • The recipient needs only an email address, a browser, and internet access — no account, keys, or software.

Secondary / out-of-band channel

  • The password. Share it over a channel separate from the email (call, text, Signal, in person). Never send it by email.
  • Any hint that travels in the email must be meaningless to outsiders.

Trust model and caveats

  • Security depends entirely on the password staying secret and travelling out-of-band.
  • The recipient must click an external link or open an encrypted attachment — which can resemble phishing, so a heads-up over the side channel helps.

Which method to use

  • Routine mail, not especially sensitive → transport encryption is automatic; nothing to do.
  • Sensitive mail to a technical contact you'll write to repeatedly → OpenPGP; exchange and verify keys once, then it is automatic.
  • Sensitive one-off to someone with no keys → password-based; agree the password by phone or text first.

Premises and caveats (summary)

  • Subject lines and metadata are not encrypted in any method — keep them generic.
  • TLS protects mail in transit only; the providers can still read it at rest unless a mailbox-encryption option is used.
  • A password must always travel over a channel other than the email.
  • A public key should be fingerprint-verified out-of-band; importing a key alone does not prove identity.
  • OpenPGP is interoperable, so a Proton, Mailfence, mailbox.org, or any other PGP user can exchange encrypted mail with one another.
  • Interface labels and feature availability differ per provider and change over time — verify in each one's documentation.
