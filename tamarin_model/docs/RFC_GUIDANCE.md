# Human-factors security requirements (machine-checked)

> Generated by `tamarin_model/tools/rfc_gen.py` from machine-checked proofs.

Each requirement below is backed by Tamarin proofs over the ceremony-mask model. A 'risk' lemma (exists-trace) shows the unsafe human outcome is REACHABLE; a 'removed_by' lemma (all-traces) shows a named lever makes it UNREACHABLE. The requirement is the normative consequence of that proof pair.
**12/12 requirements proven.**


## REQ-VERIFY-AFFORDANCE — Low-effort fingerprint comparison  ·  _PROVEN_

**Risk.** A raw hex key-fingerprint comparison is high-Effort (NASA-TLX), which triggers the Abstraction stressor: the user stops reasoning (Naive) and accepts a tampered key (a Mistake) -> the secret is encrypted to the adversary.

**Lever.** presenting the comparison via a low-effort affordance (a side-by-side visual diff), which keeps the user Attentive.

**Requirement.** Implementations MUST present key-fingerprint comparison via a low-effort affordance (e.g. a side-by-side visual diff or word-list), not a raw hexadecimal string.

**Proof backing.**
- `P2_mistake_reachable` (P2_postkdf_recovery.spthy) — risk reachable
- `P7_no_mistake` (P7_interface.spthy) — risk removed

## REQ-MFA-NUMBER-MATCH — Engaged-user value on approval prompts (number matching)  ·  _PROVEN_

**Risk.** A habituated user (repeated prompts) OR a user under adversary-induced urgency reflexively auto-approves a prompt of any kind, including an adversary-injected one (MFA prompt-bombing / fatigue).

**Lever.** requiring an engaged-user value (number matching) the reflexive user cannot supply.

**Requirement.** Implementations MUST require an engaged-user value (e.g. number matching) on security-critical approval prompts, so that a habituated or time-pressured user cannot approve an adversary-injected prompt.

**Proof backing.**
- `P2_autoapprove_injected_reachable` (P2_postkdf_recovery.spthy) — risk reachable
- `P8_adv_autoapprove_reachable` (P8_adversary.spthy) — risk reachable
- `P6_shutout_blocks_injected` (P6_mitigations.spthy) — risk removed

## REQ-KEY-CONFIRM — Detect-and-halt key confirmation  ·  _PROVEN_

**Risk.** A user under high cognitive load / time pressure slips and computes a wrong key; without a check, the ceremony completes with the wrong key (unsafe success).

**Lever.** a key-confirmation step that detects the mismatch and halts.

**Requirement.** Implementations MUST verify the derived/agreed key against an expected value and halt on mismatch, so that a slip cannot complete the ceremony with a wrong key.

**Proof backing.**
- `P1_slip_reachable` (P1_calc_pressure.spthy) — risk reachable
- `P6_no_slip_completion` (P6_mitigations.spthy) — risk removed

## REQ-DEVICE-COMPARE — Automatic (device-side) fingerprint comparison  ·  _PROVEN_

**Risk.** Leaving the fingerprint comparison to the user's mental model lets a Naive user accept a tampered fingerprint.

**Lever.** the device comparing the fingerprints automatically and refusing a tampered one.

**Requirement.** Implementations SHOULD compare security-critical fingerprints automatically (device-side) rather than relying on the user, so a tampered fingerprint cannot be accepted.

**Proof backing.**
- `P3_mistake_reachable` (P3_worstcase.spthy) — risk reachable
- `P6_no_tampered_mistake` (P6_mitigations.spthy) — risk removed

## REQ-OOB-PASSWORD — Out-of-band secret channel  ·  _PROVEN_

**Risk.** Sending a sharing password in-band (same channel as the ciphertext) lets the adversary decrypt; a Careless user takes that shortcut and leaks it silently.

**Lever.** sending the password over a channel OTHER than the message (with no degraded share, secrecy is absolute).

**Requirement.** Implementations MUST transmit a sharing password/secret over a channel other than the protected message itself.

**Proof backing.**
- `S10_inband_leak_silent` (S10_pw_inband_leak.spthy) — risk reachable
- `S2_misdelivered_pw` (S2_trio_pw.spthy) — risk reachable
- `S0_secrecy_absolute` (S0_baseline.spthy) — risk removed

## REQ-POPULATION — Cover the least-skilled intended population  ·  _PROVEN_

**Risk.** A step that is low-demand for an expert can be high-demand (overwhelming) for a novice, who then slips. A ceremony proven safe for experts may be unsafe for novices.

**Lever.** the expert population (low demand) -- which a novice does NOT enjoy; so the safety is population-scoped.

**Requirement.** The analysis/deployment MUST consider the least-skilled intended user population (the slip is reachable for novices though not experts); equivalently, the interface MUST lower the step's demand for everyone.

**Proof backing.**
- `P1_slip_reachable` (P1_calc_pressure.spthy) — risk reachable
- `P9_no_slip` (P9_population.spthy) — risk removed

## REQ-VERIFY-BEFORE-SEND — Disable the send control until verification completes  ·  _PROVEN_

**Risk.** When the composer shows the Send button CO-PRESENT with the unfinished key verification, a degraded user can authorise the send BEFORE the fingerprint has been checked at all. This is not a wrong answer to a prompt -- it is answering the prompts OUT OF ORDER, and the resulting message leaves the boundary unverified. The old model could not even express this: a ceremony whose steps are joined linearly cannot produce an out-of-order trace.

**Lever.** a forcing function: the Send control is disabled (not merely warned about) until the recipient's key has been verified, so the out-of-order grant has no route to the wire.

**Requirement.** Implementations MUST disable the send action until recipient-key verification has completed. A warning or a confirmation dialog is NOT sufficient: the degraded user grants it.

**Proof backing.**
- `S1_premature_send` (S1_trio_pgp.spthy) — risk reachable
- `S4_premature_send` (S4_worstcase.spthy) — risk reachable
- `S11_no_premature_send` (S11_hardened.spthy) — risk removed

## REQ-CONFIRM-BEFORE-SESSION — Disable session start until key confirmation completes (second ceremony)  ·  _PROVEN_

**Risk.** The SAME order violation appears in a completely different ceremony: in the manual key-establishment messenger, a degraded user presses 'start session' before the key read-back, and the session goes live on an unconfirmed -- possibly slipped or substituted -- key. The shutdown that would have caught it is simply skipped.

**Lever.** the same forcing function: 'start session' is disabled until the key confirmation read-back has completed.

**Requirement.** Implementations MUST disable session establishment until key confirmation has completed. This is the SAME requirement as REQ-VERIFY-BEFORE-SEND, proved necessary in a second, independent ceremony -- which is what makes it a general design rule rather than an artefact of one protocol.

**Proof backing.**
- `K3_premature_reachable` (K3_premature.spthy) — risk reachable
- `K5_no_unconfirmed_session` (K5_hardened.spthy) — risk removed

## REQ-NO-PLAINTEXT-FALLBACK — No silent plaintext fallback in the encryption selector  ·  _PROVEN_

**Risk.** When the encryption selector offers 'Standard (TLS only)' alongside the protected methods, a degraded user picks the wrong route and the message is handed to the provider in the clear. Nothing about the send looks unusual to the user.

**Lever.** removing the plaintext exit from the selector for a correspondent whose key is available (the composer's per-recipient lock indicator already knows this).

**Requirement.** Implementations MUST NOT offer an unprotected send route as a peer option in the encryption selector when a protected route is available for the recipient.

**Proof backing.**
- `S8_tls_misroute_chain` (S8_transcribe.spthy) — risk reachable
- `S4_tls_misroute` (S4_worstcase.spthy) — risk reachable
- `S11_no_plaintext_fallback` (S11_hardened.spthy) — risk removed

## REQ-FORWARD-GUARD — Forward must re-encrypt or block  ·  _PROVEN_

**Risk.** The recipient-side breach: every SENDER step can be perfect and the message still leaves the boundary, because a degraded recipient forwards it to a third party for whom no key exists and the client silently sends it in the clear. This is a breach of 'only the correspondents know m' that no sender-side mitigation can prevent.

**Lever.** Forward re-encrypts to the new recipient or BLOCKS -- it never silently downgrades to cleartext.

**Requirement.** Implementations MUST NOT silently downgrade a forwarded protected message to cleartext. Forward MUST either re-protect for the new recipient or refuse.

**Proof backing.**
- `S3_forward_outside` (S3_trio_mixed.spthy) — risk reachable
- `S11_no_forward_outside` (S11_hardened.spthy) — risk removed

## REQ-FIELD-REMINDER — Standing reminder on every unprotected field  ·  _PROVEN_

**Risk.** The subject line is never encrypted, and neither is a password hint -- but nothing on the screen says so. Under load the user degrades to Careless and types the secret into the field that looks like part of the protected message. The crypto is perfect and the secret still leaves in cleartext metadata. Note what the lever does NOT do: the reminded user is STILL Careless and still reaches every other careless route (the model proves the TLS misroute remains open). A reminder fixes the FIELD, not the PERSON.

**Lever.** a standing, always-visible reminder next to every field whose contents are NOT protected. It is a REMINDER, not a forcing function: the careless user still answers (the ceremony is not blocked -- S12_completes still holds), they simply do not put the secret THERE.

**Requirement.** Implementations SHOULD display a persistent indication, next to every field whose contents are not protected (subject line, password hint), that its contents are not protected. The indication MUST be visible at the moment of entry, not only in help text.

**Proof backing.**
- `S8_sigma10_closure` (S8_transcribe.spthy) — risk reachable
- `S12_no_subject_leak` (S12_field_reminder.spthy) — risk removed

## REQ-SHOW-PASSWORD — Offer to reveal a typed secret so it can be checked  ·  _PROVEN_

**Risk.** A passphrase masked as dots is UNCHECKABLE. Under time pressure the user slips, the wrong value is committed BLIND, and the message goes out protected by a passphrase the sender never intended -- while the recipient is given the one the sender meant. The failure is silent at both ends.

**Lever.** a show/hide affordance: revealing the typed value makes it CHECKABLE, so the user's own self-check catches the slip before the send. The user still slips (S13_still_slips) -- the interface simply lets them see it.

**Requirement.** Implementations SHOULD offer a reveal control for any secret the user must TYPE (as opposed to paste), so the typed value can be verified before it is committed. A value the user cannot see is a value the user cannot check.

**Proof backing.**
- `S2_slipped_pw_sent` (S2_trio_pw.spthy) — risk reachable
- `S13_no_slipped_pw_sent` (S13_pw_reveal.spthy) — risk removed
